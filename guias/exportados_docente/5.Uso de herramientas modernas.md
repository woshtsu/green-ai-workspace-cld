**Uso de herramientas modernas**

Hay una precisión importante sobre la **“última versión”**: actualmente ICACIT ya tiene publicados los criterios **2027**, aprobados en diciembre de 2025; para Ingeniería, el atributo relevante es **AG-I11: Uso de Herramientas**, que exige *crear, seleccionar, aplicar y reconocer las limitaciones* de técnicas, recursos y herramientas modernas de ingeniería y TI, incluyendo predicción y modelado, en problemas complejos de ingeniería. ([webicacit.com](https://www.webicacit.com/archivos/2027_ICACIT_Criterios.pdf?utm_source=chatgpt.com))

Para un proyecto de **Ingeniería de Sistemas e Informática/TI**, recomiendo no limitar esta competencia a "herramientas de software". Debe demostrar el uso integrado de **herramientas de ingeniería, computación, gestión, modelado, desarrollo, calidad, datos, IA y comunicación**, justificando su selección y sus limitaciones.

**1. Necesidades de herramientas**

Primero debe identificarse **qué necesita hacer el equipo**.

Ejemplo:

| **Necesidad** | **Tipo de herramienta** |
| --- | --- |
| Modelar procesos | BPMN |
| Diseñar arquitectura | UML / ArchiMate |
| Gestionar código | Git/GitHub |
| Gestionar backlog | Trello |
| Desarrollar | IDE |
| Analizar datos | Python |
| Entrenar ML | Google Colab |
| Visualizar KPIs | Power BI |
| Probar API | Postman |
| Analizar calidad | SonarQube |
| Probar rendimiento | JMeter |

La lógica es:

**Necesidad → herramienta**, no:

"Usaremos estas herramientas porque son conocidas."

**2. Criterios de selección**

La selección debe ser una **decisión de ingeniería**.

Recomiendo criterios breves:

* adecuación técnica;
* facilidad de integración;
* costo;
* disponibilidad;
* escalabilidad;
* seguridad;
* interoperabilidad;
* soporte;
* curva de aprendizaje;
* limitaciones.

Ejemplo:

| **Criterio** | **Peso** |
| --- | --- |
| Adecuación al proyecto | 25% |
| Funcionalidad | 20% |
| Integración | 15% |
| Costo | 10% |
| Seguridad | 10% |
| Escalabilidad | 10% |
| Usabilidad | 10% |

**11. Evaluación de resultados**

No basta con decir:

"Se utilizó SonarQube."

Debe decir:

"El análisis inicial identificó 35 code smells; después de la refactorización se redujeron a 12."

Igualmente:

"Las pruebas de rendimiento mostraron una reducción del tiempo de respuesta de 2.8 s a 1.4 s."

Así se demuestra **aplicación + resultado**.

La herramienta se convierte así en parte del **proceso de toma de decisiones de ingeniería**.

ICACIT 2027 formula precisamente AG-I11 como **“Crea, selecciona, aplica, y reconoce las limitaciones”** de técnicas, recursos y herramientas modernas de ingeniería y TI, incluyendo predicción y modelado. ([webicacit.com](https://www.webicacit.com/archivos/2027_ICACIT_Criterios.pdf?utm_source=chatgpt.com))

**Una estructura de herramientas que recomiendo para un proyecto TIC**

**Ingeniería**
→ UML / PlantUML / BPMN / arquitectura / simulación

**Desarrollo**
→ IDE / Git / GitHub / Docker / APIs

**Datos e IA**
→ Python / Colab / ML / Power BI

**Gestión**
→ Trello / GitHub Projects / Teams / Dashboard

**Calidad**
→ SonarQube / JUnit / Postman / JMeter

**Seguridad**
→ OWASP / SAST / DAST

**Documentación**
→ Markdown / GitHub / herramientas de diagramación

**Validación**
→ pruebas + métricas + experimentos

La clave es que **no se evalúe la cantidad de herramientas utilizadas**, sino la capacidad del estudiante para **seleccionar la herramienta apropiada, justificarla, aplicarla para resolver una necesidad de ingeniería, medir el resultado y reconocer sus limitaciones**.
