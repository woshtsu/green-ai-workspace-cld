**6.Prueba de Concepto (PoC)**

Para un proyecto TIC con **uso de IA**, la **Prueba de Concepto (PoC)** debe ser breve, experimental y orientada a demostrar que la tecnología propuesta **es técnicamente viable y aporta evidencia para continuar con el proyecto**. Para fines ICACIT, conviene vincularla con **análisis del problema, conocimientos de ingeniería, uso de herramientas modernas y gestión del proyecto**, sin convertir la PoC en un PMV.

**Plan breve de PoC para un requerimiento con IA**

**1. Identificación de la PoC**

| **Elemento** | **Definición** |
| --- | --- |
| **Requerimiento** | Requerimiento que incorpora IA |
| **Problema técnico** | ¿Qué incertidumbre tecnológica se necesita resolver? |
| **Objetivo de la PoC** | Determinar si la IA propuesta puede resolver técnicamente el requerimiento |
| **Tecnología** | ML / Deep Learning / IA generativa / SLM / LLM, según el caso |
| **Duración** | 1–2 semanas |
| **Datos** | Dataset disponible para experimentar |
| **Criterio de éxito** | Métrica técnica previamente definida |
| **Resultado** | Viable / viable con restricciones / no viable |

**2. Secuencia de ejecución**

**FASE 1. Definir la incertidumbre**

**Pregunta:**

¿Qué no sabemos todavía sobre la utilización de IA?

Ejemplos:

* ¿El modelo alcanza precisión suficiente?
* ¿Tenemos suficientes datos?
* ¿El modelo responde en tiempo adecuado?
* ¿La IA puede clasificar correctamente?
* ¿El modelo generativo produce respuestas confiables?

**Salida:** hipótesis técnica.

**FASE 2. Definir hipótesis y criterio de éxito**

Ejemplo:

**H1:** Un modelo Random Forest puede clasificar el nivel de riesgo de los usuarios con un F1 ≥ 0.85.

| **Indicador** | **Criterio** |
| --- | --- |
| Accuracy | ≥ 85 % |
| Precision | ≥ 80 % |
| Recall | ≥ 80 % |
| F1-score | ≥ 0.85 |
| Tiempo de inferencia | < 2 s |

La métrica debe ser seleccionada según el problema; no se debe utilizar accuracy automáticamente.

**FASE 3. Preparar datos**

Realizar únicamente lo necesario:

**Datos → limpieza → transformación → división → entrenamiento**

Por ejemplo:

Dataset

↓

Limpieza

↓

Preprocesamiento

↓

Train / Validation / Test

↓

Modelo IA

Registrar:

* cantidad de registros;
* variables;
* datos faltantes;
* distribución;
* calidad;
* posibles sesgos.

**4. Selección del modelo**

No es necesario probar diez algoritmos.

Seleccionar **2 o 3 alternativas razonables**.

Ejemplo:

| **Modelo** | **F1** | **Tiempo** | **Complejidad** |
| --- | --- | --- | --- |
| Logistic Regression | 0.78 | Bajo | Baja |
| Random Forest | **0.87** | Medio | Media |
| XGBoost | 0.88 | Medio | Alta |

**Modelo seleccionado:** XGBoost.

**Justificación:** alcanza el mejor desempeño dentro de los criterios establecidos, aunque presenta mayor complejidad.

Esto constituye evidencia de **selección de una herramienta/técnica de ingeniería**.

**5. Construcción del prototipo de PoC**

La PoC debe ser **mínima**.

No se necesita desarrollar todo el sistema.

Por ejemplo:

Entrada

↓

API / Notebook

↓

Modelo IA

↓

Predicción

↓

Resultado

**Ejemplo**

Entrada:

Edad = 21
Asistencia = 65 %
Promedio = 10.8

Salida:

**Riesgo académico: ALTO**
Probabilidad: 0.87

**6. Experimentación**

Ejecutar pruebas controladas.

Ejemplo:

| **Experimento** | **Modelo** | **Dataset** | **F1** |
| --- | --- | --- | --- |
| E1 | Logistic Regression | D1 | 0.78 |
| E2 | Random Forest | D1 | 0.87 |
| E3 | XGBoost | D1 | **0.88** |

También puede evaluarse:

* precisión;
* recall;
* F1;
* MAE/RMSE, si es regresión;
* latencia;
* consumo de recursos;
* costo;
* robustez.

**7. Validación de la PoC**

Comparar:

**Resultado obtenido vs. criterio de éxito**

| **Criterio** | **Meta** | **Resultado** | **Cumple** |
| --- | --- | --- | --- |
| F1 | ≥ 0.85 | 0.88 | ✓ |
| Recall | ≥ 0.80 | 0.84 | ✓ |
| Latencia | < 2 s | 1.4 s | ✓ |
| Datos | ≥10 000 | 7 500 | ✗ |

Aquí puede aparecer una conclusión importante:

**Viable técnicamente, pero requiere ampliar el dataset antes del PMV1.**

Esto es mucho más valioso que simplemente indicar "la IA funciona".

**8. Identificación de limitaciones**

Esta parte es **fundamental para la evidencia de ICACIT sobre uso de herramientas modernas**.

Registrar:

| **Limitación** | **Impacto** | **Acción** |
| --- | --- | --- |
| Dataset pequeño | Medio | Obtener más datos |
| Desbalance de clases | Alto | Aplicar técnicas de balanceo |
| Sesgo | Alto | Evaluar grupos |
| Latencia | Bajo | Optimizar modelo |
| Interpretabilidad | Medio | SHAP/LIME |

**9. Decisión Go / No-Go**

La PoC debe terminar con una decisión.

**GO**

La tecnología es viable y se puede continuar con PMV1.

**GO CON CONDICIONES**

Es viable, pero requiere resolver determinadas restricciones.

**NO-GO**

La tecnología no alcanza los criterios y debe cambiarse la alternativa.

Ejemplo:

**Decisión: GO CON CONDICIONES.**
El modelo supera el F1 objetivo (0.88 ≥ 0.85), pero la cantidad de datos disponibles es insuficiente. Se requiere ampliar el dataset antes de implementar el PMV1.

**10. Entregable de la PoC**

Para mantenerlo **breve**, exigir solamente:

**Informe PoC — máximo 5 páginas**

**1. Requerimiento con IA**

**2. Incertidumbre/hipótesis**

**3. Datos y metodología**

**4. Modelos evaluados**

**5. Resultados**

**6. Limitaciones**

**7. Decisión Go/No-Go**

**8. Recomendación para PMV1**

Y como anexos:

* código;
* dataset o referencia al dataset;
* resultados de experimentos;
* evidencias de ejecución.

**Integración PoC → PMV1 → PMV2 → PMV3**

Para tu esquema de proyectos, recomiendo esta relación:

PoC

│

¿La tecnología IA es viable?

│

┌────────┴────────┐

│ │

NO-GO GO

│ │

Cambiar tecnología ↓

PMV1

IA básica

↓

PMV2

↓

PMV3

**Diferencia clave**

| **PoC** | **PMV1** | **PMV2** | **PMV3** |
| --- | --- | --- | --- |
| ¿Es viable? | ¿Funciona? | ¿Genera valor? | ¿Está consolidado? |
| Experimental | Funcional | Integrado | Validado |
| Reduce incertidumbre | Valida solución | Mejora solución | Demuestra resultado |
| No es producto | Producto mínimo | Producto ampliado | Producto final |

**Matriz de trazabilidad para ICACIT**

Esta es la que recomiendo incorporar a la documentación del proyecto:

| **Evidencia ICACIT** | **Evidencia PoC** |
| --- | --- |
| **Análisis de problemas** | Identificación de incertidumbre técnica |
| **Conocimientos de ingeniería** | Selección del algoritmo/modelo |
| **Uso de herramientas modernas** | Python, Colab, ML, APIs, etc. |
| **Análisis y experimentación** | Comparación de modelos |
| **Gestión de proyecto** | Tiempo, recursos y decisión Go/No-Go |
| **Diseño de solución** | Prototipo mínimo |
| **Validación** | Métricas y criterios de éxito |
| **Reconocimiento de limitaciones** | Riesgos, sesgos, datos y restricciones |

**Fórmula práctica a los estudiantes**

**PoC = Requerimiento IA + Incertidumbre + Hipótesis + Datos + Experimento + Métrica + Resultado + Limitaciones + Decisión**

Y para que sea realmente **concreta y breve**, establecería como regla:

**1 requerimiento de IA → 1 hipótesis → máximo 3 alternativas tecnológicas → 3–5 experimentos → métricas objetivas → decisión Go/No-Go → recomendación para PMV1.**

Esto evita que la PoC se convierta prematuramente en un desarrollo completo y permite demostrar ante ICACIT que el estudiante **selecciona y aplica herramientas modernas, experimenta, analiza resultados y reconoce sus limitaciones**.
